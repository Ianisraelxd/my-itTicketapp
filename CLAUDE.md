# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

```bash
npm start          # everything on :3001: starts XAMPP MySQL if needed, builds dist/ when stale, creates/updates the DB, opens the browser (start.bat does the same)
npm run dev:all    # API on :3001 + Vite live reload on :5173 (proxies /api -> :3001)
npm run server     # Express API only (also serves dist/ when it exists); runs server/setup.js first
npm run dev        # Vite only
npm run build      # Production build to dist/ (recharts and the super admin screens are lazy chunks)
npm run lint       # oxlint (config: .oxlintrc.json)
npm test           # node --test server/ (priority matrix + auto-assign unit tests)
npm run qa         # scripts/qa.mjs: ~140 API checks; qa-deep.mjs (needs DB access) and qa:ui (browser walk-through) too
npm run db:init    # Wipes and recreates the DB from server/schema.sql (not needed: setup.js does the first run)
```

In production mode the API serves the built website, so one process is enough. `scripts/qa*.mjs` are the regression checks: run them against a throwaway database (`DB_NAME=helpdesk_demo PORT=3002 node server/index.js`), never the real one.

`server/schema.sql` **drops and recreates all tables**, then seeds demo accounts. Settings are optional: copy `server/.env.example` to `server/.env` (gitignored, loaded by `server/env.js` from any working directory) to override `DB_HOST`, `DB_PORT`, `DB_USER`, `DB_PASSWORD`, `DB_NAME=helpdesk`, `PORT=3001`. All seeded accounts share ID `2404154` and are distinguished by role (login requires ID + password + role); passwords are in the schema file.

## Architecture

- **Frontend is a single file**: `src/App.jsx` (~2300 lines) holds the root `App` component and every page/modal component. There is no router. `page` state (a string like `"manageRequestsPage"`) decides what renders; role-based menus come from the `navFor` map at the top, and the same map feeds both the desktop sidebar and the mobile `.bottom-nav`. Adding a page means: add a nav entry in `navFor`, add a `page === ...` render branch inside `<div className="page" key={page}>`, and write the component.
- **Roles**: `student`/`staff` (map to the "user" nav), `agent`, `admin`, `superadmin`. The superadmin sees only Dashboard, Report Manager and Activity Log Reports; user/ticket/password-request management belongs to the admin role.
- **Data flow**: `App` loads tickets, activities and (for agent/admin/superadmin) users from `src/api.js` whenever `user` or `refreshKey` changes; children call `refreshData()` after mutations. Student/staff fetch only their own tickets (`mine=1`).
- **Skills & recommendations**: agent skills live in `users.skills` (comma-separated ticket categories, shared list `SKILL_OPTIONS` in App.jsx). Admins edit them on the Users page (agent filter) and can switch an account between Staff and Agent (`PATCH /api/users/:id/role`, which fails with 409 if that ID already exists in the target role); `PATCH /api/users/:id/skills` checks the actor is an admin. `skillFit()` classifies a ticket as match / mismatch / neutral for an agent: matches sort first with a "Recommended" badge, mismatches show a "do this at your own risk" warning modal before resolving. Tickets require an explicit category (no default).
- **Chat dock**: `ChatDock` (bottom-right, Facebook-style) is rendered only for admin and agent accounts. Messages live in the `messages` table via `/api/messages*`, which reject any non admin/agent sender or recipient. It polls (5s contacts, 3s open conversations) rather than using websockets.
- **Ticket conversation & cancellation**: `src/TicketChat.jsx` (`TicketDetailsModal` > `TicketChat`) is opened from My Requests (requesters) and the agent queue. The conversation behaves like a group chat: the requester, the assigned agent and all admins share one thread per ticket (agents reach it from the queue's Chat button, admins from Manage Requests), and a new message notifies everyone else on it. Message boxes use `ChatInput.jsx` (auto-growing textarea: Enter sends, Shift+Enter adds a line). Messages live in `ticket_messages` (`kind` = `chat` | `cancellation_request` | `cancellation_decision`). Requesters can never cancel directly: `POST /api/tickets/:code/cancellation-requests` files a `cancellation_requests` row (and a chat message); admins accept/reject it from the queue at the top of Manage Requests (`PATCH /api/cancellation-requests/:code/status`), and only acceptance sets the ticket to `Cancelled` (status guard in the UPDATE). Chat is read-only once a ticket is Resolved/Done/Closed/Cancelled. **Reopening**: the owner of a Resolved ticket can reopen it (`POST /api/tickets/:code/reopen`, reason required, guarded in the UPDATE, max 3 via `tickets.reopen_count`); it returns to In Progress (or Open if never assigned), posts a `reopen` chat message and notifies the agent and admins. The UI shows a warning dialog with a confirmation checkbox first.
- **HelpDesk Assistant (ticket chatbot)**: `server/bot.js` is a rule-based, button-driven bot (`createBot(deps)` returns `registerBotRoutes`, `postGreeting`, `postResolvedPrompt`; deps are injected from `index.js`, which also owns the shared `fileCancellationRequest` / `reopenTicketFor` functions the bot calls). It is a real `users` row with role `bot` (invalid password hash, hidden from `/api/users` and role counts). Messages live in `ticket_messages` with `kind` `bot` (options in the `meta` JSON column), `bot_choice` (the requester's pick, echoed as their bubble) and `bot_note` (staff-only, filtered out of the owner's `GET /messages`). `POST /api/tickets/:id/bot { choice }` only accepts an option the last bot message offered (or `menu`). The greeting is posted after ticket creation and a rating prompt when a ticket becomes Resolved; ratings go to `tickets.csat_rating`. Bot messages never notify or count as first response. Presence: `authenticate` updates `users.last_seen_at` for agents/admins (throttled 20 s), and `staffAvailability()` treats the last 90 s as online, so the greeting, the Talk-to-a-agent answer and the chat banner say whether people can reply now. Typed messages: `POST /tickets/:id/messages` from the requester calls `bot.autoReply` (keyword intents in `INTENTS` / `PROBLEM_WORDS`, stays silent for 10 min after an agent/admin chat reply). Tagalog: `isTagalog()` + `TL_INTENTS` / `TL_PROBLEM_WORDS` understand it and `toTagalog()` / `TL_LINES` / `TL_LABELS` translate the bot's replies and chips (fix steps stay English; unknown lines fall back to English). Knowledge base for fixes is the `KNOWLEDGE` object per ticket category. UI: bubbles, quick-reply chips, typing dots and presence banner live in `TicketChat.jsx`. SQL: `server/migrations/2026-10-chatbot.sql`.
- **Smart intake & priority**: tickets are created with `locationId` (from `GET /api/locations`, cascading `LocationSelector` in `src/SmartIntake.jsx`), `impactLevel` and `urgencyLevel`; the client never sends a priority. `server/priority.js` is the pure matrix (`calculatePriorityTier`, tested in `priority.test.js` with `npm test`) plus the `calculatePriority` middleware on `POST /api/tickets`, which sets `tickets.priority_tier` (P1-P4; escalates one tier for Exam/Graduation/Lecture/Dean or `IS_FINALS_WEEK`) and the legacy `tickets.priority` label (P1/P2 High, P3 Medium, P4 Low) that reports, KPIs, SLA and the bot still read. `tickets.location` is now only a text snapshot of the chosen room for reports. `PUT /api/tickets/:id/cancel` is the admin queue-safe cancel (status guard in the UPDATE, row kept); `GET /api/agents/workload` counts Open/In Progress per agent. SQL: `server/migrations/2026-10-priority-locations.sql`.
- **Auto-assign**: `server/autoassign.js` (started from `index.js`, runs every `AUTO_ASSIGN_CHECK_SECONDS`) assigns Open tickets older than `AUTO_ASSIGN_MINUTES` (30) to an agent whose `users.skills` contains the ticket category, and expires unresolved auto assignments after the same time by moving them to another agent with that skill (`pickAgent` is pure and tested in `autoassign.test.js`). Admin assignments set `tickets.assigned_manually = 1` and are never moved. State: `tickets.assignment_started_at`, `auto_assign_count`, history in `ticket_assignments`; the engine posts an `assignment` message in the ticket chat and sends `assigned` / `reassigned` / `auto_assigned` / `auto_unassigned` notifications. SQL: `server/migrations/2026-10-autoassign.sql`.
- **Startup & setup**: `server/setup.js` runs before `listen`: it creates the database if missing, loads `schema.sql` into an empty one, and applies the missing files of `MIGRATIONS` (an ordered list with a `done()` probe each, so a migration never runs twice). When you add a migration file, add it there too, and put the same change in `schema.sql`. `server/index.js` serves `dist/` with an SPA fallback, gzip (`compression`), `RATE_LIMIT_AUTH` per-address limits on login/signup (set `TRUST_PROXY=1` behind a proxy), strict SQL mode (`db.js`), and codes (`#HD`, `#CR`, `#PW`) come from `createWithCode()` which queues requests so parallel submissions never collide. `GET /api/tickets` returns every active ticket plus the 500 newest finished ones (header `X-Total-Count`), `GET /api/activities` the newest 1000.
- **Feature modules (each in its own file in `server/`)**: `audit.js` (`logEvent()` writes `ticket_events`; the History panel reads `GET /tickets/:id/history`), `attachments.js` (photos: base64 JSON upload on a route with its own 8 MB parser registered before the global 100 KB one, content sniffed by magic bytes, random names in `server/uploads/`, served only to people on the ticket; the chat shows them as `kind = 'attachment'` with `meta.attachmentId`), `kb.js` (help articles: `searchArticles()` is shared with the bot, which suggests `kb:<id>` options for typed questions and from "More help"), `autoclose.js` (`tickets.closed_at`: a Resolved ticket becomes un-reopenable `AUTO_CLOSE_DAYS` after `resolved_at`; it stays status Resolved so KPIs do not change), `events.js` (Server-Sent Events: `POST /events/ticket` gives a single-use ticket, `GET /events?ticket=` streams `{type: notification|message}`; `notify()` and chat routes call `publish()`; the client is `src/realtime.js` and polling only slows down while connected), `mailer.js` (nodemailer; `notify()` calls `alertUsers()` for the types in `EMAIL_TYPES`; `MAIL_MODE=log` prints instead; optional `SMS_WEBHOOK_URL`; opt-out is `users.email_alerts`), `backup.js` (pure-JS SQL dump, gzip, daily schedule, `scripts/restore-backup.mjs` restores), `ratelimit.js`. Migration for all of them: `server/migrations/2026-10-features.sql` (also listed in `setup.js`). The archive pipeline copies `ticket_events` and `ticket_attachments` to `*_archive` tables too, so a new table linked to tickets needs the same treatment.
- **Sign-in safety**: the server starts a 10 second cooldown on the 5th wrong password (`COOLDOWN_AFTER`; responses carry `cooldownSeconds` / `retryAfter`) and locks 15 minutes at the 10th. The page (`src/useLoginGuard.js`, kept in sessionStorage) counts failures itself so it also covers unknown IDs: 5 wrong = 10 second countdown with the form disabled, a further wrong attempt reveals "Forgot password?". `POST /api/forgot-password` accepts an email and changes nothing (announced for the next version).
- **Role names**: the role keys are `student`, `staff` (shown as University Staff), `agent`, `admin`, `superadmin`, `report_viewer`. They used to be `employee` and `technician` (`server/migrations/2026-10-roles.sql` converts an old database); the API uses `agentId`, `/api/agents/workload`.
- **Assignment is stored server-side too**: `PATCH /api/tickets/:code/assign` (admin only) sets `tickets.assigned_to` and status In Progress; the time slot/progress shown in the UI still come from localStorage. `assigned_to` is what routes notifications to the right agent.
- **Notifications**: `notifications` table, written by the server-side `notify()` helper inside the route that causes the event (new ticket, assignment, status/resolved, ticket messages, cancellation requested/approved/declined, password request + decision, skills/role changes). Clients poll `GET /api/notifications?userId=` every 8s; new unread items pop a toast and trigger a data refresh. Superadmin has no notifications. Add new events by calling `notify([userIds], {type, title, body, ticketCode})`; map the `type` to an icon in `NOTIFICATION_STYLES` in App.jsx.
- **Sound effects**: `playSound(name)` in `src/sounds.js` (files in `public/sounds/`) is called for login, signup, message sent/received (chat dock and ticket chat) and new notifications. It debounces repeats and skips the message ding right after a notification sound. Incoming messages are detected by comparing the newest message id between polls.
- **Theme & animations**: Settings stores `theme` (light | dark | system) and `motion` (on | device | off) next to mute/volume. `applyAppearance()` in `src/settings.js` sets `<html data-theme data-motion>` (an inline script in `index.html` does the same before first paint to avoid a white flash). All colours are CSS variables in `App.css` (`:root`, overridden by `html[data-theme="dark"]`) — use the tokens (`--card`, `--surface-1/2`, `--ink`, `--ink-2`, `--muted`, `--line`, `--warn-*`, `--good-*`, `--bad-*`, `--info-bg`), never raw hex, for anything that sits on the page or a card. Animations default to **on even when the device asks for reduced motion** (that was why they looked broken on phones with reduce-motion enabled); "device" restores the OS behaviour and "off" disables them. JS-driven motion should check `motionAllowed()`.
- **Settings & version**: `SettingsModal` (`src/SettingsModal.jsx`, opened from the sidebar, the mobile header gear, or the gear on the login screen) stores `{muted, volume}` in localStorage (`helpdesk-settings-v1`) via `src/settings.js`; `sounds.js` reads them on every `playSound`. The app version string (`APP_VERSION`, also shown in the sidebar footer and About modal) lives in `src/settings.js` — bump it together with `package.json`. Don't name a component file `Settings.jsx` next to `settings.js`: Windows' case-insensitive filesystem makes the import resolve to the wrong one.
- **Report Manager**: `ReportManager` (App.jsx) loads `GET /api/reports/summary` (SQL `GROUP BY` aggregations for the current filters, superadmin only) through `useReportData`, which derives `isLoading` so `ChartSkeleton` shows while filters change. Charts go through `ReportChartContainer` (Recharts: bar / line / pie); `ReportFilters` holds the date/category/role controls (defaults from `reportDefaults.js`: last 30 days) and the CSV export button (`csv.js`, no dependency; formula-looking cells get a leading apostrophe). Database backups: `scripts/backup-database.bat` (see README).
- **KPI scorecard**: `server/kpiCatalog.js` defines the 16 metrics (key, unit, direction, default target, formula, `SLA_MINUTES`); `server/kpi.js` calculates them in SQL per month (`computeMonth`) and serves `GET /api/kpi` and `PUT /api/kpi/selection` (super admin only). Which metrics show for a month is stored in `kpi_selections`; a month without rows inherits the latest earlier choice, then `DEFAULT_SELECTION`. The time metrics rely on `tickets.assigned_at`, `first_response_at` and `resolved_at`, which the assign / message / status / reopen routes in `index.js` keep up to date (resolved_at is cleared on reopen). `GET /api/kpi/trend` returns the last N months of every metric. UI: `KpiScorecard.jsx` exports the dashboard scorecard plus `KpiScorecardView` (health ring, cards with sparklines) and `KpiPicker`, which the Report Manager reuses for the month of its *To* date together with `KpiTrendCard`; hooks `useKpiData` / `useKpiTrend`, helpers in `kpiFormat.js` (`buildKpiCards`). Full metric list: `docs/KPI-METRICS.md`; to add a metric edit the catalog and `computeMonth`.
- **Auth & governance**: `server/auth.js` is the gate (`authenticate` on all of `/api`, `requireRoles`, `verifyReportViewer` = superadmin + report_viewer for analytics endpoints, `verifySuperAdmin` for writes; `report_viewer` is read-only, any non-GET is refused). `server/security.js`: scrypt password hashing, JWT (`JWT_SECRET`), TOTP. Login has lockout (5 failures / 15 min) and optional TOTP second step (`/api/login/mfa`); the client keeps the token in `sessionStorage` (`api.js`) and restores the session via `/api/me`. `server/superadmin.js`: the archive pipeline (finished tickets older than a date -> JSON/CSV export in `backups/archives/` -> copy to `*_archive` tables -> delete, one transaction; reports/KPIs read the `tickets_all` view so history is unchanged) and `PUT /api/superadmin/manage-admins/:id` (revoke / grant / grant_viewer / unlock / reset_mfa). UI: `SuperAdminPanel.jsx` composes `ArchivePanel` + `AdminTable` (presentation) with `hooks/useArchive.js` + `hooks/useAdminManagement.js` (logic). SQL for upgrading an existing DB: `server/migrations/2026-10-enterprise.sql`.
- **Activities** travel as `[timestamp, name, role, action]` tuples (shaped in `GET /api/activities`), not objects.
- **Ticket progress is derived, not stored**: the "Agent" and "Progress" columns and the tracker in the ticket popup come from the ticket itself (`status`, `assignedName`, `cancelPending` returned by `/api/tickets`) via `ticketTracking()` in App.jsx, so every role sees the same thing. The `localStorage` assignment record (`helpdesk-ticket-assignments-v1`) is only a fallback for the agent name and the admin's time-slot text.
- **Backend**: `server/index.js` is one Express file with all routes; `server/db.js` exports a mysql2 pool and a `query()` helper (always use `?` placeholders). Tickets are keyed by a generated code (`#HD001`), password requests by `#PW001`. `/api/tickets` returns `location` and `createdAt`, which the Report Manager relies on.
- **Styling**: one stylesheet, `src/App.css`, with design tokens on `:root`, a tablet icon-rail breakpoint (≤1100px), and a phone layout (≤640px) where the sidebar is hidden and the bottom tab bar takes over. Animations respect `prefers-reduced-motion`.
- `presentation/index.html` is a standalone localStorage-based demo build, separate from the React app.

## Gotchas

- Every `/api` route except login/signup/health needs a session token: when you test with curl or a script, log in first (`POST /api/login`) and send `Authorization: Bearer <token>`. The caller's id is stamped onto `userId/actorId/senderId/createdBy/reviewedBy` by `authenticate`, so route code can trust those fields.
- Passwords are scrypt hashes now (old plaintext rows upgrade on first login). The profile endpoint never returns a password.
- When you add a column to `tickets`, `ticket_messages` or `cancellation_requests`, add it to the matching `*_archive` table and re-create the `tickets_all` view, otherwise archiving (`INSERT ... SELECT *`) breaks.
- Seeded accounts share ID `2404154`, so promoting one of them to a role another seeded account already has (same ID + role) returns 409; test role changes with an account that has its own ID.
- If Vite serves a blank page with "does not provide an export named 'default'", it cached a half-written `App.jsx`; restart the dev server.
